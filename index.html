Pacific NW X-Ray Inc.

Complete front-end redesign of a 28-year-old medical equipment dealer's website. Rebuilt the dated early-2000s layout as a modern light-theme site with clearer navigation, stronger visual hierarchy, and a mobile-first responsive build.

HTML/CSS
JavaScript
UI Redesign
Light Theme
Original Site Live Site GitHub

Overview

A complete front-end redesign of the website for Pacific NW X-Ray, a medical equipment dealer whose site had been online for roughly 28 years. This was a solo project: I handled both the design direction and the build in HTML, CSS, and JavaScript.

The Problem

The original site was built in the early 2000s and it showed: cluttered layout, weak visual hierarchy, and no consideration for mobile devices. For a business selling technical equipment, an outdated site undermines credibility and makes it harder for customers to find products and get in touch.

My Approach

I treated this as a translation exercise rather than a decoration pass: figure out what the business needs the site to communicate, then rebuild the presentation around it. I audited the original pages, identified the core visitor tasks (understand what they sell, browse products, make contact), and designed a dark, professional theme with a clear hierarchy before writing the CSS mobile-first.

Design & Development Decisions

  • Chose a light theme with a single accent color to modernize the brand and let product imagery stand out.
  • Reorganized navigation so the main visitor tasks are reachable in one click.
  • Used type scale, spacing, and section structure to build a clear information hierarchy.
  • Built mobile-first, so layouts scale up to desktop instead of being squeezed down to phones.
  • Kept the HTML semantic so the structure stays readable and easier to maintain.

Challenges & Solutions

The biggest challenge was density. A medical equipment dealer has a lot of product information, and the original site presented it all at once. I broke the content into clearly separated sections with consistent spacing so pages can be scanned instead of read. The before/after preview on this card shows how much of the improvement came from hierarchy and spacing rather than new features.

Result

A modern, responsive front end that makes a 28-year-old business look current, deployed as a live rebuild alongside the original for comparison. The project demonstrates the full redesign process: auditing an existing site, making deliberate design decisions, and translating them into a working front end.

What I Learned

How to audit an aging website, design around hierarchy and readability, and run a mobile-first CSS workflow. It also taught me that most of a redesign's value comes from structure and restraint, not from adding more.

Pott's Off-Leash Dog Sanctuary

Responsive website for a community dog sanctuary. Designed and built a layout with a video hero, donation call-to-action, volunteer sign-up, and regulation pages, organized so every type of visitor can find their next step quickly.

HTML/CSS
Non-Profit
Video Hero
Live Site GitHub

Overview

A website for a community dog sanctuary: a real organization that needed a practical web presence. I designed and built the full site, including a video hero, donation call-to-action, volunteer sign-up, and regulation pages.

The Problem

The sanctuary's visitors arrive with very different goals. Donors want a quick way to give, volunteers want to sign up, and visitors need the rules before bringing a dog. All of that has to live on one site without the important-but-dry information burying the emotional appeal that motivates donations.

My Approach

I started from visitor intent rather than from a layout. Most arrivals want to do one of three things: donate, volunteer, or plan a visit. I organized the content around those paths and led with a video hero to communicate the sanctuary's atmosphere immediately.

Design & Development Decisions

  • Used a full-width video hero for immediate emotional connection, with overlay treatment to keep text legible over motion.
  • Gave the donation call-to-action prominent placement so it is never more than a glance away.
  • Separated volunteer sign-up and regulation details into their own sections so essential information stays findable without cluttering the main message.
  • Built the layout responsive so the site works for the many visitors who will first open it on a phone.

Challenges & Solutions

The main challenge was balance: lead with feeling, but keep practical information one click away. I solved it with hierarchy. The hero and donation path carry the visual weight, while sign-up and regulation content is clearly signposted rather than competing for attention. Keeping text readable over a moving video background also took deliberate work with overlays and type contrast.

Result

A complete, deployed website that serves the organization's real needs: it tells the sanctuary's story and gives every type of visitor a clear next step. It shows I can design around user goals and business needs, not just aesthetics.

What I Learned

Designing for multiple audiences on one site, organizing content by visitor intent, working with video backgrounds responsibly, and taking a real-world project from blank page to deployed site.

// CLIENT WEBSITE — IN DEVELOPMENT, PREPARING FOR LAUNCH
IEEE Community Resource Hub

Independent website for an IEEE-affiliated student organization, referred through a professor. The school couldn't host the functionality the club needed, so I'm designing and developing a standalone multi-page site where students can learn about the organization, see upcoming and past events, and access resources. Currently nearing initial launch, with the client planning additional features and content after the first release.

HTML/CSS
JavaScript
Responsive Design
Multi-Page Architecture
Content Organization
Live Site GitHub

1. Project Overview

This is a real client project, not a school assignment. A professor recommended me to another web development professor who helps run an IEEE-affiliated student organization. The organization needed a website it couldn't build on the school's existing page, so I'm designing and developing a dedicated, standalone site for them. My role covers the full development process.

Status: the project is in development and approaching its initial launch. The core website is being finalized and prepared for deployment.

2. The Problem

The school would not allow the organization to add the website functionality it needed to the school's existing website. As a result, the organization had no dedicated web presence, and students had no single place to find information about the club, its events, and the resources it offers. The organization needed an independent site it could control and grow.

3. Goals

  • Create a dedicated online presence for the organization, independent of the school's site.
  • Make it easy for students to learn about the organization and find what they need.
  • Organize upcoming and past events in one place.
  • Centralize useful student resources and important information.
  • Deliver a professional, responsive website that works across devices and is maintainable as content grows.

4. My Role

I am responsible for the website's full build. That includes the web design, page structure, information organization, responsive implementation, and building the site in HTML, CSS, and JavaScript. I also handle content implementation and incorporate the client's revisions as we prepare the site for deployment. The client provides the organization's content, requirements, and feedback; the design decisions and the build are my work.

5. Design Process

I approached the design by starting from what students need to do, then organizing the site around those tasks. Because the content spans events, past activities, and resources, I chose a multi-page structure so each area has a clear, findable home rather than crowding everything onto one page. Navigation and information hierarchy were the priority: a student should be able to tell at a glance where upcoming events, past events, and resources live. I kept the visual treatment consistent across pages so the site reads as one cohesive product, and designed responsively so it holds up on the phones many students will actually use.

6. Development Process

I translated the design into a working site using semantic HTML for structure, CSS for layout and responsive behavior, and JavaScript for interactivity. The multi-page architecture keeps each section of content in its own file, which makes the site easier to navigate in code and simpler to extend. I kept repeated patterns, like the shared navigation and page layout, consistent across pages so updates and new content can be made in one place rather than page by page. As the site has grown through client revisions, I've tested the responsive behavior and layout as part of preparing it for launch.

7. Client Collaboration

Working with a real client is different from a personal or class project because the requirements come from someone else's needs, not my own assumptions. My job has been to translate the client's goals, like "students need to find events and resources," into concrete page structure and design decisions. I've gathered the client's content and feedback, made revisions based on it, and balanced my design judgment against what he actually wanted. Because the client plans to keep adding content and features after launch, I've also had to build with their future changes in mind, not just the first version.

8. Challenges & Problem Solving

Organizing varied content. Problem: the site has to serve several distinct needs — about the organization, upcoming events, past events, and resources — without any one burying the others. Thought process: forcing it all onto one page would make everything hard to find. Solution: a multi-page structure with clear navigation so each type of content has a dedicated, predictable place.

Designing for an unfinished scope. Problem: the client has more content and features planned after launch, so the site can't be structured as a fixed, finished thing. Thought process: if I hard-code the current content into rigid layouts, every addition becomes a rebuild. Solution: keep the structure and components consistent and modular so new content slots in without breaking the layout or navigation.

9. Current Status

This project is still in development. The core multi-page website — structure, design, responsive layout, and the initial content — is built and deployed to a live staging URL, and it is being finalized for its initial launch. Additional client-requested features, content, and improvements are planned for future iterations after the first release.

10. Result So Far

Because the project isn't finished, I won't claim final metrics. What it has accomplished so far: the organization now has a dedicated platform it controls, students have a centralized place to access information, events, and resources, and the project has progressed from the client's initial constraint — "we can't build this on the school's site" — into a functional website approaching launch.

11. What I Learned

This has been my first sustained real-client project, and the biggest lessons are about process, not just code: how to turn a vague request like "a place for students to find things" into concrete page structure and design decisions; how to design for actual users instead of hypothetical ones; how to handle revisions and changing requirements without losing the design's coherence; and how to build a site that's ready for real-world deployment and the changes that come after it.

12. Next Steps

The immediate focus is finishing the core website and deploying it for the initial launch. After that, the client has additional features, content, and improvements they want to add, which I'll implement in future iterations as the site grows.

// AI-Powered Analyst Dashboard
Vanguard Intelligence

LLM-powered dashboard for monitoring oil and energy market signals, built as a team project. I joined after the initial build and owned front-end improvements: a rebuilt chat input and loading flow, light/dark themes, full mobile responsiveness, and UI safeguards that flag weak data instead of letting the model guess.

Python/Flask
Local LLM (Ollama)
Data Dashboard
Team Project
GitHub

Overview

A team-built, LLM-powered web scraping dashboard that helps analysts monitor oil and energy market signals in one place (Python/Flask with a local LLM via Ollama). I joined after the initial dashboard and chat interface had been built; my role centered on the front end: usability, responsiveness, and making the quality of the data visible in the UI.

The Problem

The core system worked, but the interface had not caught up. The chat input and loading flow gave poor feedback, the layout assumed a desktop screen, and, most importantly for an analyst tool, the LLM could present confident-sounding output built on weak data without the interface warning anyone.

My Approach

Because this was an existing codebase, I started by reading, not writing: understanding the structure and conventions before changing anything. Then I listed the friction points from actually using the dashboard and worked through them one at a time, keeping each change small and consistent with the patterns already in place.

Design & Development Decisions

  • Rebuilt the chat input and loading flow so users always know the system is working and what it is doing.
  • Added light/dark themes through CSS variables so the entire interface switches consistently.
  • Made the dashboard fully responsive so analysts are not tied to a desktop.
  • Implemented source reliability scoring and live API health monitoring in the UI so data quality is visible at a glance.
  • Built a filterable price chart, plus safeguards that identify weak signals instead of allowing unsupported guesses.

Challenges & Solutions

The hardest part was the trust problem: an analyst tool that occasionally presents weak data confidently is worse than one that admits uncertainty. My solution was to move reliability into the interface itself, through source scoring, API health indicators, and weak-signal flags, so the user can judge the output instead of blindly trusting it. Working inside code I did not write was its own challenge; matching established conventions mattered more than rewriting things my way.

Result

The project concluded with a live demonstration, cost analysis, and presentation to the board. For me it proved I can step into a team project, find the highest-value improvements, and ship them without disrupting the team's work.

What I Learned

Reading and extending an unfamiliar codebase, designing UI around data quality and trust, making information-dense layouts responsive, and presenting technical work to non-technical stakeholders.

// Interactive Game
Rock Paper Scissors React Rebuild

A rebuilt version of one of my first JavaScript projects, recreated with React and Vite to improve structure, state handling, and maintainability. I kept the original design to showcase how my design and coding skills have developed over time.

JavaScript
CSS Art
Game Logic
Live Site GitHub

Overview

Rock Paper Scissors started as one of my first JavaScript projects. I built a playable browser version with HTML, CSS, and JavaScript while learning the basics. Later, I rebuilt the same game with React and Vite so I could compare how the same project changes when you move from direct DOM scripting to a component-based approach. I kept the original visual design on purpose so the comparison stays focused on how much my coding approach and project structure improved compared to my newer designs.

The Challenge

In version one, I was focused on learning core programming: writing logic, handling user clicks, updating the interface, and keeping game state accurate after each round. At that stage, even small issues like missed state updates or repeated logic blocks were hard to spot. Rebuilding later gave me a way to solve the same problem with better structure and a clearer mental model.

Version 1: HTML, CSS & JavaScript

The original version taught me how programming concepts connect in a real interface. I used variables to track selections and score, conditionals to decide round outcomes, and functions to keep repeated logic manageable. Event listeners connected user input to gameplay, and DOM manipulation displayed the result of each round. I also implemented random computer choices and score/result tracking, which helped me understand how data, logic, and UI have to stay in sync.

The Rebuild: React + Vite

I rebuilt the project because I wanted to understand React in a practical way, not just from tutorials. Using a familiar game let me focus on architecture changes. I broke the interface into components, moved game data into state, and used event handlers and conditional rendering to drive the UI from state instead of manually updating DOM nodes in multiple places. Vite gave me a faster development loop and cleaner project setup, which made iteration easier.

What Changed Between Versions

In the JavaScript version, I was mostly thinking in terms of "find element, change element" after every interaction. In the React version, I shifted to "update state, let the UI re-render from that state." That changed the structure of the code a lot. The rebuilt version is easier to reason about, easier to extend, and less fragile when making updates.

Problem Solving & Lessons Learned

This project taught me that getting an app to work is only step one. The bigger lesson was learning how to organize logic so it stays readable and maintainable. Building the same app twice helped me compare approaches directly and understand the difference between writing working code and writing code that is easier to maintain and expand.

Outcome

The finished rebuild shows my progression from learning core JavaScript fundamentals to understanding modern front-end development with React. It is still a simple game by design, but it clearly demonstrates growth in how I structure UI, manage state, and approach problem solving.
